## 宏入口与流程

1. `赛事报名_CommandButton1_Click`：读取赛事名称和逗号分隔的组别，删除并重建“报名表”，预建 500 行；字段为序号、车号、车手、领航员、车型、车队、组级、备注及动态分组列。然后重建“赛事信息”表，写入赛事名、分组文本和分组数量。
2. `赛段成绩_CommandButton1_Click`：读取赛段数、前缀和 0.01/0.001 精度；从报名表读取连续车号，生成各赛段表、总成绩表和分组成绩表。赛段表的 H/J 输入紧凑时间，K/M 转为 Excel 时间，N=收车−发车+罚时，O 使用升序 `RANK.EQ`。总成绩用 `XLOOKUP` 汇总各赛段，分组成绩用 `SUMPRODUCT` 计算组内名次。
3. `CommandButton1_Click` / `CommandButton2_Click`：分别显示“赛事报名”和“赛段成绩”窗体。
4. `CommandButton3_Click`：删除除“启动页”外的所有工作表，属于破坏性清理操作，源码没有二次确认。
5. `GetColLetter`：将列号转换成 A~ZZ 范围内的列字母。

## 移植到小程序时必须处理的行为差异

- 车号读取在遇到第一行空车号时停止，并且循环条件 `row < 500`，实际最多读到第 499 行；报名表虽然预建到第 501 行，尾部两行不会被统计。
- 只要分组单元格有任意非空字符就改写为 `√`；没有去重、空白组名或组名合法性校验。
- 时间输入依赖固定长度数字字符串；赛段表默认输入全 0。未录入的车辆仍参与 `RANK.EQ`，总成绩也可能把未完成赛段按 0 累加，不能直接当作正式比赛排名。
- 结束时间小于发车时间时会得到负时长，没有跨午夜、DNS、DNF、罚时合法性和重复车号处理。
- 旧表删除范围只包括本次传入的赛段前缀和数量；改前缀或减少赛段时可能残留旧表。删除期间 `DisplayAlerts` 在循环的 `finally` 中恢复，后续删除可能重新弹出警告。
- 宏固定使用 `Application.Workbooks.Item(1)`；移植时应改成当前赛事/当前云端数据，不要依赖打开顺序。
- `信息表.Visible = -1` 的注释写成 `xlSheetVeryHidden`，但在常见 Excel 枚举中 -1 通常是可见；目标 WPS 环境需验证后再决定小程序是否隐藏该配置。
- 源码使用 `alert` 和 `Application.Alert` 两种提示方式；小程序移植应统一为页面状态/Toast，并将生成过程改成可恢复的异步事务。

## 推荐的小程序数据模型

- `events`：赛事基本信息、分组、赛段配置和时间精度。
- `registrations`：车号、车手、领航员、车型、车队、组别，多组报名用数组保存。
- `stageResults`：赛事 ID、赛段、车号、发车时间、收车时间、罚时、状态（正常/DNS/DNF）。
- `rankings`：服务端按已完成赛段和规则计算，客户端只展示；管理员修改数据后重新计算版本。

报告生成于静态分析阶段；`NewMacros.js` 是提取的原始代码，不能直接在微信小程序运行。
